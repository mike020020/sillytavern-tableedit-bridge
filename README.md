# 正文 `<tableEdit>` 状态块填表工具包（sillytavern-tableedit-bridge）

把「正文里顺手写一个 JSON 状态块 → 卡内脚本按 DDL 校验并写进 shujuku（SP·数据库）表格」这套做法打包出来：
**表格更新确定、可控、可校验，且不再需要每轮额外调用一次填表 AI**。

## 包里有什么

| 文件 | 用途 |
| --- | --- |
| [`tableEdit-bridge.js`](./tableEdit-bridge.js) | 状态桥脚本（卡内酒馆助手 / JS-Slash-Runner）。表名/列名是占位示例，改 `SCHEMA` 即可用 |
| [`worldbook-协议条目模板.yaml`](./worldbook-协议条目模板.yaml) | 世界书协议条目模板（YAML，便于阅读与改写） |
| [`worldbook-协议条目模板.json`](./worldbook-协议条目模板.json) | 同一份协议的 SillyTavern 导入格式（由 YAML 解析生成，两份永远一致） |
| [`examples/`](./examples) | 9 个示例状态块 + 期望结果（装上包就能逐条对照，含错误示例与多标签用例） |
| [`docs/状态栏跨表取数.md`](./docs/状态栏跨表取数.md) | 配套文档：前端（状态栏）**从表格取数**的完整方法——找表/找列/找行、跨表取数五种手法、快照组装、刷新去抖、性能与 10 个常见坑 |
| [`README.md`](./README.md) | 本文件：快速开始 + 完整技术原理与实现细节（即下文的「技术原理」部分） |

一句话分工：**协议条目**告诉模型「允许写哪些表、哪些列、什么格式」；**桥脚本**把这些声明变成校验与写库。

两篇配套阅读：**写进去**看本 README 的「技术原理」；**读出来**看 [`docs/状态栏跨表取数.md`](./docs/状态栏跨表取数.md)（状态栏如何跨表取数、如何拼快照、如何刷新与排错）。

## 三步装好

1. **贴脚本**：打开 `tableEdit-bridge.js` 整段复制，贴进酒馆助手（JS-Slash-Runner）新建脚本，脚本名建议「结构化状态同步桥」。
   脚本顶部的 `SCHEMA` 是表/列白名单——把 `demo_state` / `demo_npc_state` / `demo_npc_profile` 换成**你自己卡模板里的物理表名**，
   把 `example_*` 换成对应表的 DDL 列名（枚举、范围、正则、长度、默认值都写在列声明里）。
2. **加协议条目**：把改好的表/列规则写进世界书（二选一）
   - 方式 A：世界书面板 → 导入 → 选 `worldbook-协议条目模板.json`；
   - 方式 B（推荐）：新建条目，把 `worldbook-协议条目模板.yaml` 的 `content` 整段粘进去，再按自己的表改。
   - 建议设为 **constant（常开）**、位置 `Before Char`；条目里的表名/列名要**与脚本 SCHEMA 完全一致**。
3. **关掉这几张表的自动填表**：数据库插件模板里把走状态块的表 `updateConfig.updateFrequency` 设为 `0`
   （`-1` 是「跟随全局」，不等于关闭），然后回包 / 重新导入模板。

装好后每轮：正文末尾带一个状态块 → 桥自动校验并写库；写不进去会给出明确原因（见下文「自测与排错」）。

## 30 秒自测

在任意聊天里手打一条（表名换成你自己的）：

```text
<tableEdit>
{"updates":[{"table":"demo_state","where":{"row_id":1},"set":{"example_time":"2026-01-01 12:00"}}]}
</tableEdit>
```

点脚本按钮「同步最后一条状态」：应提示「已写入 N 项」，表格里对应单元格变化；再点一次应提示「这条状态已经同步过」。

## 从零实现的最小 checklist

按顺序做完这 8 条，就能在自己卡里跑通（不依赖任何其它文档；细节查阅下文对应小节）：

1. **确认表格运行时可用**：卡里已在用 shujuku（SP·数据库）表格模板，且脚本能拿到 `window.AutoCardUpdaterAPI`（宿主不同时它在 `parent`/`top` 上）。
2. **列出可写表与列**：决定哪几张表走状态块，逐表写下物理表名（DDL 表名）与允许写的列、类型/范围/枚举/格式/长度、`where` 定位键。
3. **写桥的 SCHEMA**：把第 2 步的清单抄进 `tableEdit-bridge.js` 的 `SCHEMA`（列多的档案表可加 `insertFillMissing: '未知'`）。
4. **写世界书协议条目**：按 `worldbook-协议条目模板.yaml` 的 `content` 逐表列出同样的约束，设为 **constant**（常开），表名/列名必须与 SCHEMA 完全一致。
5. **放脚本并接事件**：脚本贴进酒馆助手，确认按钮「同步最后一条状态」出现、事件钩子已注册（收到回复后会自动尝试同步）。
6. **关掉这几张表的自动填表**：模板里把它们的 `updateConfig.updateFrequency` 设为 `0`（`-1` 是跟随全局，不等于关闭），其余表保持原样，然后回包 / 重新导入模板。
7. **按示例自测**：依次跑 `examples/01`→`09`，重点确认「能写、能更新、能去重」「错误整块拒绝且表格不变」「只取最后一对标签」。
8. **验一次真实回复**：正常玩一轮，确认正文末尾产出状态块、表格被更新；再看控制台有无异常，必要时调 `minWaitMs` / `quietMs`（见下文「与自动填表抢窗口怎么办」）。

## 边界与前提

- 需要卡里已经在用 shujuku（SP·数据库）表格模板；脚本按 9.x 的公开 API 编写（见文末「桥用到的 API」）。
- 工具包只提供「桥骨架 + 协议条目模板」，**不含任何角色卡内容**；表名、列名、枚举都要按你自己的卡改。
- 与数据库插件自动填表可以共存：只把走状态块的表关掉自动填表即可；两者抢窗口时的处理见下文「与自动填表抢窗口怎么办」。

# 技术原理与实现细节

## 用正文 `<tableEdit>` 状态块直接填表（状态桥实现说明·通用版）

> 本文记录一种**不依赖数据库插件自动填表**的写库方式：正文末尾输出一个 `<tableEdit>` JSON 状态块，
> 由卡内酒馆助手脚本「结构化状态同步桥」解析、按 DDL 校验后写入 shujuku（SP·数据库）表格——
> 效果等价于执行 `UPDATE` / `INSERT`，但不需要额外调用一次填表 AI，也不受自动填表频率与批次影响。
>
> 适用场景：卡内已有 shujuku 表格模板；希望表格更新**确定、可控、可校验**，或想省掉自动填表的 token 成本。
>
> **本文所有表名、列名、角色名、路径都是占位示例**（形如 `demo_*`、`example_*`、`NPC甲`、`<卡项目>`），
> 照做时替换成你自己卡模板里的真实物理表名与 DDL 列名即可。桥脚本的对象名、文件路径也由各卡自定。

---

### 零、怎么套用到你的卡（三步）

1. **写协议条目**：在世界书里加一条 `constant: true` 的协议条目（见第四节），逐表列出可写表与列约束；
2. **放桥脚本**：把「结构化状态同步桥」脚本装进卡里（酒馆助手 / JS-Slash-Runner），并让它读到你卡里的表；
3. **改模板配置**：把走状态块的表 `updateConfig.updateFrequency` 设成 `0`（见第五节），再回包。

之后每轮回复末尾会带一个状态块，桥自动校验并写库；出问题看第六节的报错表。

---

### 一、为什么可以用状态块替代自动填表

| 维度 | 插件自动填表 | 正文 `<tableEdit>` + 状态桥 |
| --- | --- | --- |
| 触发者 | 数据库插件按 `updateConfig` 另起一次填表 AI 调用 | 正文模型在写剧情时顺手输出状态块 |
| 成本 | 每轮（或每 N 轮）× 每组的额外 token | 零额外调用，只多几十字 JSON |
| 内容一致性 | 填表 AI 只能看到表格与上下文片段，容易漏剧情细节 | 状态块由写正文的模型产出，天然与剧情一致 |
| 可控性 | 频率/批次由插件决定，出错难定位 | 表名、列名、取值都被白名单与 DDL 约束住，出错有明确提示 |
| 失败表现 | 静默不更新或整批失败 | 整个状态块被拒并弹出具体原因，正文不受影响 |

**注意**：两者不必二选一。实践中常见做法是「只有列多、需要长期维护的表走状态块，其余表继续用插件自动填表」——
因为插件填表能在正文漏写细节时补一手；关掉哪些表由你按第五节的 `updateFrequency` 决定。

#### 1.1 数据流（一次回复里发生了什么）

```text
                     ┌───────────────────────────── 一次回复 ─────────────────────────────┐
 世界书协议条目 ─注入─▶│ 正文模型写剧情 …………………………… 正文末尾输出 <tableEdit>{JSON}</tableEdit> │
 （允许写哪些表/列）   └────────────────────────────────────────┬───────────────────────────┘
                                                               │ 楼层落库（生成结束）
                                                               ▼
                        桥脚本（卡内酒馆助手 / JS-Slash-Runner）
                        ① 取文：ChatMessage.message / chat[].mes / swipes[swipe_id]
                        ② 取块：最后一对 <tableEdit> … </tableEdit>（容错见 3.1）
                        ③ 校验：表白名单 → 列白名单 → 类型/范围/枚举/格式/长度/必填（整块先过一遍，见 3.2）
                        ④ 规划：同表同键合并为一次写入；新增行补默认值/占位值
                        ⑤ 写入：exportTableAsJson → 定位行 → updateRow / updateCell / insertRow（见 3.3）
                                                               │
                                                               ▼
                          shujuku 表格（运行时 + 聊天持久化）
                                   │                                   │
                       refreshDataAndWorldbook                 registerTableUpdateCallback
                                   ▼                                   ▼
                          世界书重新注入                            状态栏等前端刷新
```

关键点：整条链路上**没有任何额外 AI 调用**——校验规则来自卡内的协议条目与脚本里的 SCHEMA，
写入走 shujuku 的公开 CRUD API，因此结果可复现、可断言。

#### 1.2 成本与收益（量级）

| 项目 | 插件自动填表 | 正文状态块 + 状态桥 |
| --- | --- | --- |
| 额外 AI 调用 | 每轮（或每 N 轮）每组一次 | **0** |
| 每次调用的上下文 | 表格 DDL + 当前数据 + 填表提示词（通常上千 token） | 0（状态块本身几十～几百字符） |
| 延迟 | 填表 AI 的生成时间（数秒～数十秒） | 无（跟正文一起产出） |
| 失败成本 | 整批失败，需要重试或手动追平 | 单次状态块被拒并给出原因，正文不受影响 |
| 内容来源 | 填表 AI 看表格 + 上下文片段，可能漏剧情细节 | 写正文的模型自己产出，天然与剧情一致 |

省下的是「每轮一次填表调用」；代价是**模型要自己把变化写全**——所以协议条目要把表/列约束写清，桥要把拒绝原因说清。

### 二、协议长什么样

正文末尾（状态同步块位置）输出一个标签块，标签内部只能是合法 JSON：

```text
<tableEdit>
{"updates":[{"table":"demo_npc_state","where":{"npc_name":"NPC甲"},"set":{"example_score":15,"example_tag":"初识","example_time":"2026-01-01 08:30"}}],
 "inserts":[{"table":"demo_state","row":{"row_id":1,"current_location":"某地点","example_flag":"否","example_counter":"项A=0,项B=0"}}]}
</tableEdit>
```

没有状态变化时输出空块：

```text
<tableEdit>{"updates":[],"inserts":[]}</tableEdit>
```

字段含义：

| 字段 | 说明 |
| --- | --- |
| `updates[].table` | 物理表名（DDL 表名，如表 `demo_state`、`demo_npc_state`） |
| `updates[].where` | 行定位键：单行表用 `{"row_id":1}`；按名字定位的表用唯一列，如 `{"npc_name":"NPC甲"}`、`{"quest_name":"某任务"}` |
| `updates[].set` | 要写入的列与值，**只写本轮真正变化的列** |
| `inserts[].table` / `inserts[].row` | 新增一行的表名与列值；单行表只允许在开局初始化时插入 `row_id=1` |

#### 2.1 与 SQL 的对照

| SQL 写法 | 状态块等价写法 |
| --- | --- |
| `UPDATE demo_state SET example_time='…' WHERE row_id=1` | `{"table":"demo_state","where":{"row_id":1},"set":{"example_time":"…"}}` |
| `UPDATE demo_npc_state SET example_score=15 WHERE npc_name='NPC甲'` | `{"table":"demo_npc_state","where":{"npc_name":"NPC甲"},"set":{"example_score":15}}` |
| `INSERT INTO demo_npc_state (npc_name, example_score) VALUES ('NPC乙', 0)` | `{"table":"demo_npc_state","row":{"npc_name":"NPC乙","example_score":0}}` |
| `INSERT ... ON CONFLICT DO UPDATE`（upsert） | 桥内置：目标行不存在时自动转插入，存在时转更新 |
| DDL 的 `NOT NULL` / `CHECK` / `UNIQUE` | 桥按同一份 DDL 校验（必填、范围、枚举、长度、格式） |

也就是说：**状态块 = 受约束的 SQL DML**，但模型不需要（也不允许）直接写 SQL。

### 三、桥内部做了什么

#### 3.1 取到状态块

1. **取文通道**：优先酒馆助手 `getChatMessages()` 返回的 `ChatMessage.message`；兼容 SillyTavern 原生 `chat[].mes`；兼容刮擦楼层 `swipes[swipe_id]`；标签被 HTML 实体转义（`&lt;tableEdit&gt;`）也能识别。
2. **容错**：闭合标签允许带空格（`</tableEdit >`）、标签允许带属性（`<tableEdit …>`）；未命中状态块时提示「读到 N 条消息 / 来源 / 末条开头」，便于排查。
3. **消息去重**：以「楼层 ID + 状态块内容哈希」为键，同一条状态块重复同步只生效一次（重渲染、切 swipe 不会重复扣钱、重复加数值）。去重集合要放在**全局共享**的位置（例如顶层窗口对象），否则每个渲染中的楼层各有一份桥脚本实例时会重复写。
4. **取块规则＝最后一对 `<tableEdit>` … `</tableEdit>`**：
   - 正文的思维链/说明区里可能出现 `<tableEdit>` 字样（后面还跟着别的内容），若按「第一对标签」截取，会把中间那一大段文字当成 JSON 体，报 `JSON 解析失败：Unexpected token …`，真正的状态块反而用不上。
   - 实现：列出所有 `<tableEdit>` 开标签，**从后往前**为每个开标签配它后面第一个闭标签，取第一段能 `JSON.parse` 成功的块——正常就是正文末尾那一对；全部失败时在报错里注明「共出现 N 个 `<tableEdit>` 标签」。
   - **不要**为了规避多标签，在世界书里写「只允许出现末尾这一个 `<tableEdit>`／思维链里不要写出该标签」之类约束：这类措辞会压低模型输出状态块的意愿，导致整轮不产出状态块（正文效果反而更差）。这条由桥自己兜住。

#### 3.2 校验（写之前全部过一遍）

| 校验项 | 行为 |
| --- | --- |
| 表名白名单 | 只允许协议里列出的表；其余表名（含中文表名、`sheet_` 前缀）直接报错 |
| 列名白名单 | `set` / `row` 的键必须是该表 DDL 列名（`where` 只允许定位键）。**宽容模式（默认）**：未知列只丢弃该列并提示（`xxx 没有可写列「yyy」，已忽略该列`），同一块的合法更新照常写入；**严格模式**：未知列整块拒绝并报 `xxx 不允许写入列：yyy` |
| 类型与范围 | 整数列必须是整数且落在 DDL 区间内（示例：`example_score` 取 -100~100） |
| 枚举 | 只能取约定值（示例：`example_flag` 只能「是/否」） |
| 格式 | 正则约束（示例：`example_time` 必须 `YYYY-MM-DD HH:MM`；`example_counter` 必须是 `项A=N,项B=N` 这种定长格式） |
| 长度 | 超长文本**截断并提示**（示例：`example_tag` 超过 10 字会截断），保证可写入性 |
| 必填 | 新增行缺少无默认值的必填列时报错，不会写出半条脏数据 |
| 新增行缺列自动补占位 | 列多、后续无人回填的表（如人物档案表）可配置 `insertFillMissing: '未知'`：缺列在**计划阶段**自动补占位（枚举列取第一个合法值）并提示「缺少 …，已补「未知」」。理由：只写必填列会留下空白单元格，而数据库插件的填表 AI 会**跳过已有行的空白列**，档案会永久缺项；反过来整块拒绝也不行——模型不会因为被拒就在下一轮补全，只会让同块合法更新一起丢 |

越界字段的两种模式：

- 宽容模式是**默认**行为：模型偶尔会跨表照搬列名（典型是给没有该列的表写 `updated_at`），只丢这一列比作废整块合法更新更划算。
- 严格模式：`window.__tableEditBridgeConfig.strictColumns = true`（示例名；脚本内也可调 `window.TableEditBridge.setStrictColumns(true)`）。
- 建议两种模式都在回归脚本里各写几条断言（见 6.3）。

##### 3.2.1 拒绝粒度（哪些问题废掉整块、哪些只丢一点）

| 类别 | 处理 | 例子 | 为什么这么选 |
| --- | --- | --- | --- |
| 表名不在白名单 | **整块拒绝** | `{"table":"中文表名"}`、`sheet_xxx` | 写错表等于写错数据，宁可拒绝 |
| `where` 定位键不合法 | **整块拒绝** | 单行表写 `row_id=2`；用非定位列当键 | 定位错会写错行，风险最高 |
| 类型 / 范围 / 枚举 / 格式违规 | **整块拒绝** | 整数列写 `"十五"`；枚举外取值；时间格式不对 | 这些值本身不可信，写进去就是脏数据 |
| 未知列（该表没有这一列） | 宽容模式：**丢这一列 + 提示**；严格模式：整块拒绝 | 给没有该列的表写 `updated_at` | 只丢一列比废掉同块其它合法更新划算；要更严就开严格模式 |
| 文本超长 | **截断 + 提示** | 短标签列写了 30 字 | 保留可写入性，同时明确告知 |
| 新增行缺列 | 有默认值 → 补默认值；配了 `insertFillMissing` → 补占位（如「未知」）；否则 **报错** | 档案表只写了姓名 | 空列会被插件填表 AI 跳过，档案会长期缺项 |
| 目标表读不到 | **拒绝该表并报错**，不退化成插入 | 表未导入 / 导出内容为空 | 退化成插入会撞 `UNIQUE constraint failed`，还会产生重复行 |
| 行/列/单元格被 UI 锁定 | 跳过被锁部分 + 提示 | 在表格 UI 里锁了某行 | 尊重用户显式设置的锁（上游填表也尊重） |

一句话：**「定位/类型类」错误整块拒绝，「多余/超长/缺列」类错误局部处理并提示**。

#### 3.3 写入

1. 先 `exportTableAsJson()` 读取当前表内容（兼容 `sheet_*` 键对象与「表名 → 二维数组」两种返回结构）。
2. 按 `where` 在表头里定位真实行；单行表固定 `row_id=1`；行/列定位同时认「显示名（native 模式表头）」与「DDL 列名（SQLite 模式表头）」，避免在 SQLite 模式下定位不到而误判成新行。
3. 行存在 → `updateRow`（失败回退逐列 `updateCell`）；行不存在 → 补齐 DDL 默认值后 `insertRow`。
4. 同一张表同一个定位键在一次状态块里出现多次时**合并为一次写入**（后者覆盖前者）。
5. 写入前查 `getTableLockState('sheet_<物理表名>')`：**被 UI 锁定的行/列/单元格不写**并提示说明（上游填表同样尊重这些锁）。
6. 写入统一用对象形式并带 `skipNotify: true`（`updateRow({ tableName, rowIndex, data, skipNotify })`、`updateCell({ tableName, rowIndex, colIdentifier, value, skipNotify })`、`insertRow({ tableName, data, skipNotify })`），避免触发别人注册的表格更新回调。
7. 读不到目标表内容时**直接报错跳过**，不退化成 `insertRow`（否则会撞 `UNIQUE constraint failed`）。
8. 全部写完后调用 `refreshDataAndWorldbook()`，并按需触发 `registerTableUpdateCallback` 让前端（状态栏等）刷新。

#### 3.4 触发方式

| 入口 | 说明 |
| --- | --- |
| 脚本按钮「同步最后一条状态」 | 手动同步最后一条含状态块的楼层 |
| 手动越权 | 手动点击若被「填表仍在进行」拦下，弹出确认框：确认即**跳过全部闸门**直接写一次（真在填表会被上游拒绝并回到排队，不会写坏数据）。等价入口示例：`window.TableEditBridge.forceSync()`（可在 Quick Reply / STscript / 控制台里调） |
| `MESSAGE_RECEIVED` / `MESSAGE_UPDATED` / `MESSAGE_SWIPED` / `GENERATION_ENDED` / `MESSAGE_RENDERED` | 收到、编辑、切换 swipe、生成结束、渲染完成后自动同步（延迟 300–500ms 等楼层落库） |
| 流式结束事件 `STREAM_TOKEN_RECEIVED_FULLY` | 流式生成结束时再兜底同步一次 |

多实例：每个渲染中的楼层各有一份脚本实例。为避免同一事件被跑 N 遍，用「活跃实例标记」只让最新那份处理事件（手动按钮不受限）。

提示语义：`状态已同步（N 项）` / `这条状态已经同步过` / `状态块未生效：<具体原因>` /
`最后一条回复没有 tableEdit 状态块（读到 N 条消息，来源 X，末条开头：…）`。

#### 3.5 与「数据库插件自动填表」抢窗口时怎么办

数据库插件在填表期间会**拒绝外部表格写入**（报 `AI 填表正在进行中，已拒绝外部表格写入（source=…）`），
而且此时任何写入都会让它的基线失效、整轮填表失败（白烧一次 API 调用）。桥的应对：

1. **填表开始信号**：注册插件的「填表开始」回调（它**没有**「填表结束」回调），把「填表进行中」状态挂在**顶层窗口**上全局共享，并给所有可达的 API 实例都注册一次；
2. **写入闸门**：只有「填表停止按钮不在 DOM」+「距收到消息 ≥ 起等时间」+「距最近一次表格写入 ≥ 安静期」全满足才写；事件驱动的那一次同样要过闸门；
3. **探测结束**：因为拿不到「结束」通知，只能用一次**试写**去确认（被拒＝还在填表，退回等待）。试写按 30s → 45s → 60s 退避，超过 10 分钟改为 5 分钟一次慢等，**不放弃**（放弃会留下死等状态）；
4. **过期判定**：「填表进行中」标记若已安静超过 3 分钟且填表 UI 不在，视为过期，允许试写一次；
5. **手动越权**：你确认填表早已结束时，直接点按钮走越权即可立刻同步（见 3.4）。

取舍说明：这套机制**不做 DOM 轮询**（只挂事件与一次性 timer），代价是状态块同步会晚于回复（正常约 1 分钟内，遇到填表更久）。

##### 3.5.1 闸门状态机

```text
                 收到回复 / 手动点击 / 到期重试
                              │
                              ▼
                    ┌───────────────────┐  填表停止按钮在 DOM（只读哨兵）
                    │ 闸门（canWriteNow）│◀─────── 命中 ──▶ 排队，等下一个 tick
                    └─────────┬─────────┘
                              │ 全满足：无哨兵 + 距回复 ≥ 起等 + 距最近表格写入 ≥ 安静期
                              ▼
                       写入一次（updateRow / updateCell / insertRow）
                              │
              ┌───────────────┴────────────────┐
              ▼                                ▼
      写入成功 → 清空排队/标记            被上游拒绝（AI 填表进行中）
      （状态块同步完成）                        │
                                                ▼
                                   标记 running=true，退避重试
                                   30s → 45s → 60s（上限 60s）
                                   超过 10 分钟 → 5 分钟一次慢等（不放弃）

  特殊路径：
   · probe（试写）    ：唯一允许绕过「running 标记」的路径，用来确认填表是否结束；
                        仍必须过「无哨兵 + 时间门槛」；被拒就退回排队。
   · force（手动越权）：唯一允许绕过「填表 UI 哨兵」的路径，只在用户点确认框后触发；
                        真在填表会被上游拒绝并回到排队，不会写坏数据。
   · 过期判定        ：running 标记若安静（无表格写入、无填表 UI）超过 3 分钟，视为过期，
                        事件触发即可试写一次。
```

| 状态 | 含义 | 何时进入 | 何时离开 |
| --- | --- | --- | --- |
| 空闲 | 可以正常写 | 初始 / 写入成功 | 收到回复或检测到填表 |
| 排队（queued） | 有状态块待写，但被闸门或标记挡住 | 闸门未满足 / 检测到填表 / 撞到拒绝 | 试写成功 |
| 填表中（running） | 认为插件正在填表 | 收到「填表开始」回调 / 写入被拒 / 看到停表按钮 | 试写成功（或安静超 3 分钟视为过期后试写成功） |

### 四、世界书协议条目要写什么

协议条目是桥的「对外契约」，条目内容至少包含：

1. **固定格式**与「无变化时输出空块」；
2. **可写表范围**：只列允许写的表，并逐表列出可写列；
3. **字段硬性规则**：表名用物理表名、列名用 DDL 列名、整数写数字、`where` 只能写定位键、禁止跨表照搬列名；
4. **类型/范围/枚举/格式/长度**：与 DDL 一一对应（可直接抄 DDL 注释）；
5. **填表通道说明**：哪些表已关闭自动填表、状态一律走状态块、模板表按 `groupId` 升序与 `orderNo` 连续排列；
6. **新增行规则**（可选）：列多的表要求「首次建档必须写全整行，未知内容写「未知」/「无」」。

条目建议设为 `constant: true`（每轮都在上下文里），否则模型可能忘记协议。

### 五、与模板配置的联动

1. **关闭自动填表**：把对应表的 `updateConfig.updateFrequency` 设为 `0`。
   - `-1` 表示「跟随全局设置」，**并不等于关闭**；`0` 才是这张表不再自动填。
   - 只关走状态块的那几张表，其余表继续让插件填表（互补）。
2. **分组与顺序**：`updateConfig.groupId` 用于分组，`orderNo` 用于展示/处理顺序。
   - 同一 `groupId` 的表要连续排列，`orderNo` 不要重复（重复会让填表/展示顺序不确定）。
3. **模板改动后**：重新回包，卡内那份模板条目（通常是一条隐藏条目里的 base64/JSON）才会同步。
4. **建议**：把「按 groupId 排序 + 重排 orderNo + 指定表归零」写成一个幂等的小脚本放进 `<卡项目>/tools/cards/<卡标识>/`，每次改模板后跑一遍。

### 六、自测与排错

#### 6.1 最小自测

在任意聊天里手打一条（表名/列名换成你自己卡里的）：

```text
<tableEdit>
{"updates":[{"table":"demo_state","where":{"row_id":1},"set":{"example_time":"2026-01-01 12:00"}}]}
</tableEdit>
```

点脚本按钮「同步最后一条状态」，应提示「状态已同步（1 项）」，表格里对应单元格变化；再点一次应提示「这条状态已经同步过」。

更完整的自测建议用一个**假 API + 假聊天**跑桥源码（不必开 SillyTavern）：喂不同写法的状态块，断言错误与表格结果。

#### 6.2 常见报错与处理

| 提示 | 含义 | 处理 |
| --- | --- | --- |
| `表不允许或表名不符合 DDL：xxx` | 写了不在白名单的表名（中文表名、`sheet_` 前缀、拼写错误） | 改用物理表名 |
| `xxx 不允许写入列：yyy` | 列名不在该表白名单（严格模式下整块拒绝） | 用 DDL 列名，或把该字段加进协议与桥的 SCHEMA，或关掉严格模式 |
| `xxx 没有可写列「yyy」，已忽略该列` | 宽容模式下的未知列 | 正常保护；需要整块拒绝就开 `strictColumns` |
| `xxx 不能大于/小于 N`、`只能是 …`、`格式必须是 …` | 与 DDL 约束冲突 | 按提示改值；这类错误整块拒绝，不写半条 |
| `xxx 超过 N 字，已截断为「…」` | 文本超长 | 属正常保护；让模型写短标签 |
| `xxx 新建行缺少必填列：a、b` | 新增行缺无默认值的列 | 补上必填列，或先 `updates` 再建档 |
| `xxx 缺少 …，已补「未知」` | 该表配了 `insertFillMissing`，插入行漏列并已补占位 | 属正常兜底；建议让协议要求写全整行 |
| `xxx 第 N 行已被锁定，已跳过` / `xxx 列「yyy」已被锁定，已跳过` / `xxx 单元格 R:C 已被锁定，已跳过` | 该行/列/单元格在 shujuku UI 里被锁定 | 属正常保护；要写就先解锁 |
| `xxx 读不到当前表格内容，已跳过写入以避免重复插入` | 目标表没导入或导出内容读不到 | 确认模板已导入 / 刷新后重试（防止退化成 insert 撞 UNIQUE） |
| `AI 填表正在进行中，已拒绝外部表格写入` | 插件正在填表，外部写入被拒 | 桥会自动排队重试（见 3.5）；确认填表已结束可手动越权 |
| `最后一条回复没有 tableEdit 状态块（…）` | 楼层里没有状态块或取文失败 | 看提示里的「读到 N 条消息 / 来源 / 末条开头」定位 |
| `tableEdit 状态块 JSON 解析失败：…` | 标签在但 JSON 非法（或匹配到了思维链里的游离标签） | 按提示里的内容片段修正；桥已改为取最后一对标签 |

#### 6.3 回归脚本（建议自建）

放进卡项目（示例路径 `<卡项目>/output/temp/`），用 `node` 直接跑，最少覆盖：

| 脚本 | 用途 |
| --- | --- |
| 桥写入回归 | 取文通道（`message` / `mes` / `swipes` / 实体转义）、表与列白名单、DDL 约束（类型/范围/枚举/格式/长度/必填）、同键合并、去重、锁定跳过、读不到表即拒插 |
| SCHEMA ↔ DDL 对齐 | 桥里的列清单与模板 `sourceData.ddl` 逐项对比（列名、必填、长度、枚举） |
| 模板配置核对 | `groupId` 升序、`orderNo` 连续、指定表 `updateFrequency=0`、卡内模板与文件一致 |

### 七、注意事项

- 正文**不要再输出 SQL 代码块、`UpdateVariable`、`JSONPatch` 或旧变量路径**，只保留一个状态块。
- 一次回复只输出一个 `<tableEdit>` 块；同表同键多次写入会被合并。
- 状态块由桥校验，**不要绕过桥**直接用插件界面改表结构；表结构变更仍走模板 + 回包。
- 自动填表关闭后，表格初始化仍由插件模板导入完成；某张表需要「开局建档」，就把它写进开场指令或协议条目里。
- 旧卡迁移：只需替换桥脚本与协议条目、按需更新模板条目，聊天变量与旧表数据都不受影响。
- 不要把「禁止思维链出现 `<tableEdit>`」这类约束写进世界书（会压低输出意愿）；多标签由桥兜（见 3.1）。

### 附：桥用到的 shujuku（SP·数据库 9.x）API

| API | 用途 |
| --- | --- |
| `exportTableAsJson()` | 读当前表内容（定位行/列） |
| `updateRow(tableName, rowIndex, data)` / `updateCell(...)` / `insertRow(tableName, data)` | 写表；支持对象形式并可带 `skipNotify` |
| `getTableLockState(sheetKey)` | 读取 UI 表格锁，避免覆盖被锁定的行/列/单元格 |
| `registerTableFillStartCallback(fn)` | 感知「AI 填表开始」（**没有**「填表结束」回调） |
| `registerTableUpdateCallback(fn)` | 感知表格更新（用于安静期判断与前端刷新） |
| `refreshDataAndWorldbook()` | 写完刷新数据与世界书注入 |

> SQL 分组 API（`executeSqlQuery` / `querySql` / `executeSqlBatch` 等）是 **runtime-gated**：只有在 SQLite runtime 就绪后才可见，
> 不保证存在的宿主里会返回 `null`，因此读取最好以 `exportTableAsJson()` 为主、SQL 为可选加速。

### 附二：桥源码骨架（可直接抄）

同目录的 **`tableEdit-bridge.skeleton.js`** 就是这份说明的可运行骨架：结构、判定顺序与真实实现一致，
表名/列名全是占位示例（`demo_*` / `example_*`），不含任何具体角色卡的内容。用法：

1. 打开骨架文件，把 `SCHEMA` 换成你自己卡模板里的**物理表名与 DDL 列名**（其余代码基本不用动）；
2. 整段贴进酒馆助手（JS-Slash-Runner）脚本，脚本名建议「结构化状态同步桥」；
3. 按第四节写世界书协议条目，按第五节把走状态块的表 `updateFrequency` 设成 `0` 并回包。

骨架里几个**容易抄错**的点：

1. `done`（去重集合）与 `fillState`（闸门状态）必须挂在**顶层窗口**上：每个渲染中的楼层各有一份脚本实例，挂在各自 `window` 上会导致同一状态块被重复写、闸门状态互相看不见。
2. `ensureHooks()` 要遍历**所有**可达的 API 实例去注册回调：上游可能只从顶层窗口发「填表开始」通知，只注册一个实例会漏掉。
3. 事件钩子用 `instanceToken`（活跃实例标记）只让最新那份实例干活；**手动按钮不受此限**（用户显式操作）。
4. `writeEntry`：更新走 `updateRow`（对象形式 + `skipNotify`），插入走 `insertRow`；`readRows` 返回 `null` 时**直接抛错**，绝不退化成插入（否则会撞 `UNIQUE constraint failed`）。
5. 只有**试写（`probe`）**允许绕过「填表进行中」标记、只有**手动越权（`force`）**允许绕过填表 UI 哨兵；两者都只是「允许尝试」，被上游拒绝就回到排队，不会写坏数据。
